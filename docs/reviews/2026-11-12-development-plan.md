# PennyHarvester 开发与重构计划

基线：`abc13a3142247dab427af74ea45f27738c87a117`，2026-11-12。

对应审查：[代码审查与证据](./2026-11-12-code-audit.md)。本文描述后续实施任务，不表示已经修改业务代码或完成修复。优先修复财务与状态正确性，再拆模块、测性能；不以覆盖率或文件行数代替验收。

阅读路径：第1–3节明确数据与测试约束；第6节账本状态机、第8节交易协议、第9节API/前端为具体修复；第7节模块拆分、第4节性能应在语义稳定后推进；第10节给出合并波次，第11节列出开发入口和检查方式。

## 1. 开发约束

- 不修改已有生产数据来“配合”新算法；迁移必须先备份、验证、明确回退方法。
- 保持账户、场所、网络、协议、抵押品隔离；不能跨币种求和。
- 实盘的 unknown 必须保持 unknown；不补造成交、收益、最终结算或到账状态。
- 所有有副作用的操作先建立可恢复的持久化身份；重试不得重新创建经济上相同的订单。
- 可用于展示的数据不自动获得可用于成交、止损、结算的资格。
- 保持现有离线测试与竞态检查通过；新增故障路径测试先复现再修复。
- 不以拆微服务或引入分布式基础设施替代当前单进程业务不变量。

## 2. 先补行情可信度契约

### 2.1 最小数据来源模型

不要只在全局加一个“最近扫描时间”。单次扫描的不同市场可能来自缓存、不同视图或不同接口，必须保留实际数据来源。

建议最小字段：

```text
DataProvenance
  venue
  endpoint_id             # 脱敏且稳定的来源标识，不含 API key
  network_id / protocol   # 涉及交易、结算时必填
  fetched_at              # 成功取回时间，不随缓存命中刷新
  source_timestamp?       # 上游提供才填写；不存在时保持空
  completeness            # complete / partial / unknown
  stale                   # true / false
  stale_reason?

ScanHealth
  attempted_at
  last_success_at
  views_attempted / views_succeeded
  received / accepted / rejected
  page_truncated
  errors[]                # 有界、脱敏
```

这是一份待实现的语义草案，不是当前 API 已有字段。先在内部 DTO 与测试夹具落地，再向前端添加兼容字段；不把所有现有实体强行包装成泛型框架。

### 2.2 DAT-01：缓存降级与交易门槛

实施点：`backend/internal/market/gamma.go`。

1. 缓存记录只在新响应成功且解析通过后更新 `fetched_at`。
2. 降级读取保留旧时间及失败原因；增加独立 `last_attempt_at`，不覆盖成功时间。
3. 配置不同用途的时效策略。展示可短时降级，但所有自动决策必须明确处理 stale；具体时长由实测上游延迟与策略容忍度定，不硬编“通用安全秒数”。
4. 后续页失败、部分视图失败、解析拒绝行都写入完整性状态。
5. API 展示成功数据和降级原因；不把部分失败包装成全成功，也不因一个市场坏行抹掉所有可用市场。

验收：用可注入时钟复现 24h 缓存 + 连续 503、混合成功视图、恢复响应、超过陈旧上限等情况。旧缓存被多次读取后年龄只能增长；恢复前不能重新获得 fresh 资格。

### 2.3 DAT-02 / DAT-03：解析、最终性与价格分层

实施点：`backend/internal/market/market.go`、`backend/internal/market/gamma.go` 及相应测试。

- 身份：市场 ID、token 非空且唯一；数组长度与结果顺序一致；协议标识完整。
- 数值：输入有限、价格在 `[0,1]`；计数、流动性、成交量必须按字段真实单位解释。不要把不同场所的 liquidity 名称相同视为经济含义相同。
- 解析失败：保留结构化拒绝理由及计数。全坏行返回 degraded/error，不能等同健康的空市场。
- 最终性：closed 仅是交易状态，unknown / proposed / disputed 均不产生最终兑付；明确 final 状态才允许按结果结算。
- 价格：参考价、最新成交、可执行买卖价、最终兑付价分别标识，不互相默默回退。
- 终局检查独立于选股阈值，不允许因接近 1 就自动成为“确定结果”。

验收：0/1 合法边界、1.2/-0.2 非法边界、closed+缺状态的 0.5/0.5 与 1/0、明确平局、提出结果后争议、缺 winner、重复 token、坏日期、全坏行。

### 2.4 DAT-04：协议能力明确化

- 建立 `known-supported / known-unsupported / unknown` 的交易能力判断。
- `positionIds` 与 `clobTokenIds` 的来源必须保留；不再用 `!IsV2()` 表示“可按 V1 执行”。
- instrument 的网络、协议、合约、抵押品、精度、token ID 一起匹配签名实现。
- 未知组合可展示，但禁止签名或广播；返回可操作的原因。
- Protocol V2（ExchangeV3/PositionManager、EIP-712 domain version `3`）支持属于独立升级任务；此处不指 CTFExchangeV2/domain version `2`。完成官方向量与费用/抵押品核实前，保留当前对明确标为 `v2` 市场的拒单保护。

## 3. 验证策略

### 3.1 故障夹具优先

| 层级 | 必备场景 | 通过标准 |
| --- | --- | --- |
| 行情单测 | 陈旧降级、坏行、分页失败、未知协议、缺最终性 | 数据质量可辨，错误不变成交易依据 |
| 交易契约 | 部分成交、多页成交、状态变化、提交超时、重复回调 | 无重复经济效果，数量/金额可追溯 |
| 账本事务 | 各持久化步骤失败、重启后恢复 | 不出现半完成的订单/持仓/余额 |
| 网络配置 | 主网/测试网切换、RPC chainId 不匹配 | 不在错误网络签名或发交易 |
| API | 无效输入、作用域遗漏、配置并发、凭据脱敏 | 拒绝危险输入且不泄露秘密 |
| 前端 | 账户快速切换、轮询旧请求、失败响应、状态刷新 | 不跨账户展示数据或发出错误账户操作 |
| 迁移 | 旧库 fixture、多次重复运行、中途失败 | 数据不丢失，约束可验证，升级可恢复 |

矩阵中的跨模块场景是目标，不是本次已跑过的测试；具体缺陷、编号及优先级以审查文档为准。每个实施切片必须继承审查文档对应编号的全部验收；本文列出的场景是重点提示，不替代该清单。

### 3.2 CI 与环境

- 持续执行 `go test -race ./...`、`go vet ./...`、前端类型检查与构建。
- 增加前端组件/行为测试后纳入 CI；没有测试文件时 `npm run build` 不能充当交互回归。
- 保留 Linux / Node 22 / `go.mod` 对应版本的矩阵。本次 macOS / Go 1.27.3 / Node 26 通过不是对其替代。
- 离线测试完全移除 `PREDICTFUN_LIVE`；设置为 `0` 仍会触发当前联网 guard。
- 生产 smoke 独立流水线，显式 opt-in，采用专门测试账户和额度；普通 CI 不继承密钥。
- 重点检查账本恢复、网络隔离、状态机边界，而非先追求某个统一覆盖率百分比。

## 4. 性能优化按证据推进

当前已测到的只是构建体积与测试耗时，没有真实市场规模、浏览器延迟或交易吞吐量基准。主入口 JS 587.20 kB，charts 430.21 kB；不得承诺未经测量的倍数提升。

### 4.1 建立代表性离线基准

- 场景：少量/大量市场、多账户、长订单历史、单场所故障、上游延迟和 429。
- 用 fixtures 或本地 mock 固定数据形状；需要生产分布时先匿名化并获授权，不复制密钥。
- 记录扫描总耗时、各阶段耗时、请求数量、缓存年龄、失败/截断数、goroutine、内存、数据库查询数和锁等待。
- 浏览器记录首次交互、路由切换、轮询响应、渲染次数、请求取消和错误恢复；固定设备/网络条件。
- 报告原始条件、至少多轮分位数和样本数量。先定义性能预算，再判断优化有效。

### 4.2 低风险优化次序

1. 去除重复工作和无界历史读取；先证明结果和作用域不变。
2. 对可以批量请求的行情采用批量接口；保持上游限流与有界并发。
3. 不在全局互斥区内等待不相关外部网络；调整前先建立状态一致性测试。
4. 大页面按路由动态加载；只在需要时加载图表。不要只把同样同步加载的代码换一个 chunk 名称。
5. 建立性能回归阈值后再引入缓存；缓存必须携带时效、网络和配置版本，不能重复 DAT-01。

## 6. 账本与执行优先切片

### 6.1 LED-01：统一风险准入

第一版最小修复不必引入复杂预留系统：任一未决状态或未决读取失败都禁止该账户新增风险；人工与自动入口使用同一 guard。事件、市场、总限额在调用执行器前统一校验，补账保留 EventID。

若后续要允许多个未决单并存，再引入与订单同事务落库的风险预留。计算口径应为“已确认开放敞口 + 未决最坏可成交敞口”，以终态成交/撤销证据释放，超时不能自动释放。已有历史空 EventID 必须先回填可证实的值；不能靠猜测事件关联让限额看起来正确。

验收场景至少包括：手动/自动交叉下单、未知回报后重试、同事件不同市场、恢复订单后重新检查限额、数据库查询失败。成功标准不是某函数返回 error，而是 mock 执行器没有收到第二次越限的经济操作。

### 6.2 LED-02 / LED-06：拆开交易、参考结算和链上赎回

不要把所有操作塞进一个 `pending/filled/rejected` 状态列，再靠 Reason 文本判断恢复路径。

建议最小语义：

| 类型 | 持久化关键字段 | 状态语义 |
| --- | --- | --- |
| CLOB 订单 | account/venue/network、签名订单身份、外部 order id、累计成交及已入账量 | intent → submitted/unknown → working/partial → filled/cancelled/rejected；匹配/链上确认按场所补充 |
| 参考结算 | position、结果版本/证据、终局时间、可结算剩余数量 | unresolved → finality_verified → ledger_applied |
| 链上操作 | operation id、position、chain id、from、nonce、tx hash、receipt、确认策略 | intent → signed → broadcast → confirmed/reverted；unknown/replaced 单列 |

这些是待设计状态而非直接改 enum 的迁移指令。外部场所缺少某项证据时保持 unknown，不能虚构。

实施顺序：

1. 对有未决卖出的仓位暂停不可逆结算，先修 LED-02。
2. 为赎回建立按仓位和操作类型的原子占位；不再扫描近 500 条订单。
3. 以结构化字段保存交易身份和 hash，不以展示文本作为恢复索引；broadcast 不记成 confirmed。
4. 增加独立链上恢复器，不复用 CLOB LookupOrder 查询 tx hash。
5. 对每个外部副作用的前后崩溃点注入故障，重启后能区分“未提交、已提交未知、已确认”。
6. 已关闭仓位后出现真实成交时进入 discrepancy 状态，继续阻断新增风险，直到差异被可审计地修复。

### 6.3 LED-03：风险维护先于、独立于机会发现

短期先保证 ListOpen 全失败不跳过已持仓的维护，完整风险阶段用一个明确的有界 context 覆盖 DB读、行情补查、对账、DB写。不得只为 HTTP 延长时间，最后却用过期 context 落账。

中期将循环拆成两个可单测阶段：

- `maintainRisk`：对账未决、刷新持仓、处理止损、验证终局、记录异常。
- `discoverOpportunities`：拉市场、分类筛选、费用/盘口资格、候选展示及新增风险。

名称仅为职责示意。可以仍由同一 scheduler 调度，不必立刻多 goroutine。各 venue 的预算按实际剩余时间分配；关键风险工作不因第一个慢源耗尽全部机会预算而消失。缺少单个持仓市场数据必须作为单仓不可用返回，不能被 batch=nil error 吞掉。

### 6.4 LED-04 / LED-05 / LED-07：配置和初始状态也要原子

- 配置更新短期补齐逆序回滚；回滚失败让受影响执行器进入不可交易状态，展示实际应用失败原因。中期采用候选配置快照，全部校验后切换 generation。
- baseline 不在普通 Dashboard 请求中随意初始化；使用 compare-and-set，一次初始化失败或竞争失败后重读。输入必须是同一口径的新鲜钱包/持仓快照。
- PF APIKey 纳入加密加载、保存与旧值升级；原始数据库 payload 的测试应包含所有实际认证秘密。
- 不能因为“加密了私钥”就忽略其他 API 凭据，也不能把本地加密等同于防御已控制进程的攻击者。

### 6.5 LED-08 / LED-09 / LED-10：真实性和查询热路径

- 模拟退出使用独立的市场费用来源，不依赖当前候选列表；费率未知必须显式标记，不把低默认值伪装成实测费用。
- `first_auto_entry_at` 只来自有成交证据的订单。历史“首次尝试”如需保留另设指标；修复后重新计算展示，不改真实成交记录。
- 将 snapshot 与完整 Dashboard 解耦；读模型分开放仓位、已实现汇总、是否曾交易、分页历史。
- 为 pending/unknown 查询添加与谓词一致的部分索引，用 EXPLAIN 与大历史夹具确认空结果也能迅速定位。
- 在仍由同一交易锁串行决策的范围内复用风险汇总，随成功账本事务更新；不要引入失效规则不清的全局长寿命缓存。

## 7. 模块重构边界与迁移方式

当前 `engine.go` 约 3254 行、`engine/types.go` 约 1384 行、`store/sqlite.go` 约 1244 行；大文件本身不是缺陷，关键是职责交织妨碍故障状态测试。重构目标是把已确认的不变量放到单一责任点，不重新搭建一套空目录框架。

建议先在原 package 内提取，保持外部接口稳定：

| 边界 | 职责 | 不应再承担 |
| --- | --- | --- |
| ScanCoordinator | 预算、调度、各源健康状态 | 直接完成订单/仓位落账 |
| RiskGate | 统一手动/自动准入、未决风险 | 拉取全市场列表或渲染指标 |
| OrderReconciler | 外部状态、累计成交、幂等入账 | 根据最后参考价推断真实成交 |
| PositionLifecycle | 剩余数量、退出/结算互斥、差异冻结 | 广播链上交易 |
| RuntimeConfig | 候选快照、验证、原子切换/回滚 | 在单个字段更新中留下部分生效状态 |
| LedgerQueries | 资金/历史/快照的明确读模型 | 经 UI Dashboard 间接计算账本写入 |

每次只提取一个责任点，先保持行为等价并跑测试，再单独修复语义，避免把机械搬迁和财务规则变化混在一个不可审查的大 diff。

数据库改变遵循：新增可空/默认字段 → 双读兼容 → 按确定证据回填 → 校验不变量 → 新写路径启用 → 最后收紧约束。涉及订单身份、成交或网络信息的未知历史值不得任意填“默认主网/已成交”。升级前后运行相同账本汇总，对差异逐笔解释；破坏性迁移不得只靠回滚代码而无数据恢复方案。

## 8. 交易适配器修复切片

### 8.1 PF-01 / PF-02 / PF-07：先修协议契约，不用宽松 mock 自证

实施点：`backend/internal/predictfun/client.go`、`backend/internal/predictfun/executor.go`。

1. 固定官方OpenAPI/SDK版本及取样日期，保存最小脱敏fixture；上游变更单独审查，不在CI临时拉“最新版”改变预期。
2. 请求结构使用明确DTO：create的data内含order及策略字段，cancel为data.ids，cursor接口用after。每个端点按真实字段层级建模，不共用随意递归map解析器。
3. 严格mock拒绝多余或错误层级，验证Content-Type、签名原文、query和字段类型；响应必须包含真实嵌套结构，而非专为当前解析器扁平化。
4. 订单身份与成交事实分开。外层id不能阻止读取内层order；数量、均价和费用来自可归属该订单的matches，不用请求的数量/限价倒推实际结果。
5. 撤单返回值确认哪些id实际removed、noop、rejected；取消失败的部分单仍须跟踪，不能仅忽略错误后按已结束返回。
6. 每个分页列表显式终止条件、游标重复检测、ID去重、上限和incomplete状态。

验收：严格create/cancel、真实嵌套GET、部分MARKET已终止、LIMIT仍OPEN且累计成交增加、跨页/重复页/页数上限、缺失费用与明确零费。PF订单状态恢复不能以“amountFilled>0”替代终态与完整性。

### 8.2 PM-01 / PM-03 / PM-04 / PM-05 / PF-03：统一成交事实，不统一错误假设

先明确跨适配器账本接口，再分别实现两场所映射。建议最小成交表示：

```text
ExecutionEvidence
  order_identity / trade_ids
  cumulative_or_delta          # 固定接口约定，禁止调用方猜测
  quantity_gross / quantity_net
  collateral_gross / collateral_net
  fee_amount / fee_asset
  fee_known                    # 0 != missing
  matched / confirmed / terminal
  complete                     # 页数、关联成交与累计数量已核对
  source / observed_at
```

不要求一次添加所有字段；先用契约测试固定必须的数量、gross、fee资产和终态。费用资产不能都折成同一币种再假装真实现金扣款：PF买入扣份额、卖出扣USDT；PM费用按已验证协议与实际回报分别处理，不能套用PF规则。

- PM直接Sell与Lookup路径都返回同一gross契约，engine只扣一次。
- PM逐成交计费或使用实际fee；只拿VWAP时无法精确恢复非线性费用，保留估算属性。
- PM匹配、重试、失败、确认独立于本地filled；分页不全或查询失败不能回退限价入账。相同trade重复出现不得重复记账。
- 明确拒单识别固定SDK的错误类型；网络超时仍未知。订单404的时间启发式不能独立释放全部风险。
- PF买入账本增加净份额，现金按实际支出；费用0必须与未知区分。

验收至少包括：PM100份@0.75的直接/补账净额一致；双价格逐笔费用；60+40跨页；FAILED但size_matched非零；MATCHED→RETRYING→FAILED；PF100份@0.5、200bps的净98份/现金50；maker零费；累计回报重复与增加；所有入口最终账本守恒。PM-05另覆盖固定SDK返回success=false及OrderRejectedError、随后订单404时应为rejected；提交超时后404仍保持unknown，不将任意4xx一概视为确定拒绝。

### 8.3 PM-02 / PM-06 / PF-08：Quote、计划和签名共享精确约束

建立每场所一个可测试的order plan，而非Quote和Buy各写一套滑点算法。

- 精度从明确的instrument/metadata获取；签名金额保留整数或精确十进制，float只作策略近似/展示。
- 把预算、最大价格、tick、步长、手续费、最小份额、允许部分成交一起纳入计划。
- 量化后重新检查整数maker/taker的有效限价、预算与盘口交叉；先确定可表示金额再生成对应份额，不分别截断后假设仍一致。
- Quote输出绑定计划身份、有效时间和配置generation；提交前重新验证市场变化，不能承诺预览一定成交。
- tick来自同一快照，更新时失效固定SDK缓存。若需fork依赖，保留最小补丁、上游出处及可移除条件。
- PF深度统计只计限价以内可成交档位；最优价+固定滑点与扫深度得出的最差价格不能同时作为两套真相。

验收2@0.98的实际签名整数交叉；0.07/0.01不跳tick；tick从0.01变0.001；PF预算10、ask0.5×1+0.6×100时预览和执行边界一致；最高价与最大现金永不因量化放宽。

### 8.4 PF-04 / PF-05 / PF-09 / PF-10：终局和链上身份独立修复

- PF终局必须由最终状态与按固定版本契约解码的无冲突完整结果（含明确平局）共同确认；缺结果保持unknown，不沿用缓存0.5/0.5。明确平局与参考价均衡不是一回事。
- network→默认RPC/合约/币种形成单一配置；显式RPC也查询eth_chainId匹配。错链拒绝，不能只换签名chainID。
- 赎回携带持久化MarketID及合约/结果身份，直接查询已解决市场，不依赖OPEN市场扫描碰巧热缓存。
- 交易在发送前保存from、nonce、chainID、可恢复的签名交易或hash。SendTransaction错误不自动代表未广播；receipt超时保留hash和unknown。
- 当前成功路径已等receipt，保持status=0拒绝；按明确确认策略处理重组/替换。确认receipt与钱包到账一致性分层展示。
- 重新发起同一经济操作前先恢复原交易，而不是清除pending继续占新nonce。

验收resolved缺winner/冲突/平局；testnet无RPCoverride；RPC错链；进程冷启动后赎回resolved市场；发送后响应丢失、receipt超时、status0、重启恢复、重复请求。先使用本地RPC fake，真实链小额验证另行授权。

### 8.5 PM-07 / PM-08 / PM-09 / PM-10 / PF-06：客户端真实性与身份

- 所有异步缓存写回带配置generation；余额、JWT、metadata、stats分别核对。旧响应不得进入新钱包/网络的缓存，不能靠简单清缓存解决在途请求。
- allowance保留spender身份，按实际目标合约查询；missing、zero和error不合并。
- 钱包识别展示candidate/verified，核对chain、已知factory/implementation、owner；未知不默认为可用Deposit。
- 带认证头的client限定同源重定向或禁跳转，拒绝TLS降级；测试L2/relayer/SDK内层，而非只改最外层client。
- 余额查询、钱包检测设置整体deadline；仅在单次调用内去重重复RPC，再考虑有界并发。

验收配置A请求在切B后返回；目标spender零但另一个有额度；无关minimal proxy、Safe无signer、错chain；跨主机302不带认证头。禁止在日志/fixture中保存生产key。

## 9. API、安全与前端事实模型

### 9.1 WEB-01 / WEB-08 / WEB-09 / WEB-10 / LED-07：访问边界与秘密

- 写请求有独立Origin/Host/CSRF策略，不依赖是否开启密码。可信Host与允许Origin使用显式配置，不反射请求头自动信任；与合法非浏览器客户端兼容策略一起设计。
- JSON端点限制媒体类型；不把CORS当完整CSRF防线。无密码仍视为有交易能力的敏感本地服务。
- 无反代时关闭Gin trusted proxies；有反代时只信任明确网段。登录额度在昂贵哈希前原子消耗，另设并发上限。
- 口令验证流程带credential revision，验证完成和签发会话之间复核；改密后所有旧代验证结果失效。
- 按venue定义秘密字段；PF API key同时覆盖数据库加密、GET/PUT脱敏、mask round-trip、清空/继承、日志与错误。旧库明文迁移须备份和可验证，不能只改新写入。

验收外站空体POST不触发fake执行器、text/plain拒绝；X-Forwarded-For轮换和并发失败仍限速；旧密码验证跨改密不能签发；所有系统响应和原始存储payload不含测试秘密。

### 9.2 WEB-02 / WEB-03 / WEB-07 / WEB-11 / LED-04：一次配置操作的端到端一致性

需要四个明确对象：stored override、effective runtime、editable draft、applied revision。UI不能把草稿说成已生效，也不能把空override默认写成主网地址。

1. 保留旧API时明确flat与venues的优先级；当前patch先写规范表示，再Normalize，避免旧block覆盖本次输入。
2. patch读取、合并、校验、持久化位于同一原子边界；或携带expected revision并返回409。扫描间隔等局部保存也遵守。
3. runtime全量切换/回滚覆盖所有执行器；保存响应返回真正applied revision，而不只是用户提交的候选值。
4. approval/redeem等副作用请求绑定expected revision；dirty或保存中禁止点击，确认框显示已应用chain/signing address/目标合约。
5. probe结果返回实际network、effective endpoint和所验证的能力；候选REST也必须被真正检测。钱包/网络变更后强制刷新授权状态。

验收A→B→清空的API/持久化/runtime三方一致；并发独立patch不丢字段；PF应用失败PM回滚；主网runtime+测试网draft无法误授权；继承测试网地址不会被保存为显式主网。LED-04另覆盖存储失败与回滚失败：恢复成功时持久化、runtime、UI及revision一致；恢复失败时受影响执行器不可交易，并明确展示实际状态。

### 9.3 WEB-04 / WEB-05 / WEB-06 / WEB-12：异步结果不越过事实边界

- HTTP失败文案分为确定拒绝和结果未知；未知立即禁重复操作并按持久化身份查询，不能写“订单未提交”。
- 长链上操作返回operation id并可查询；服务端有界deadline与HTTP WriteTimeout协调。仅延长超时不能解决断线后的未知结果。
- 草稿与所有probe/detect/save响应都绑定revision；旧结果无论success/error/finally都不得更新新草稿。
- Quote key至少包括account、venue、token、金额、配置revision；改金额立刻失效，TTL/过期/失败可见。显示“盘口估算”，不把估算标为最终真实收益。
- JSON解析错误和body AbortError传播，只有协议明确204/空body才允许空结果；轮询显式request generation。

建议先引入轻量组件测试工具，复用现有技术栈。必须采用可控制Promise顺序/时间的夹具，不能只做快照测试。

验收A慢B快逆序、保存后编辑、probe通过后换key、headers成功body损坏、hide/show交错、报价1→100、服务端处理成功客户端断线、操作恢复查询。

### 9.4 WEB-13 至 WEB-20：可见状态与操作入口

- 分页/venue列表绑定accepted query key和observed_at；旧数据只能以原查询标签展示。失败保留数据同时显示stale，不能换页码伪装新结果。
- offset越界自动纠正重查或保留返回入口；Dashboard子查询独立展示刷新错误。
- 本地乐观engine状态只存到权威响应返回，不能永久覆盖轮询。
- 赎回使用pending-ID集合或明确账户串行，handler再做live/venue检查；desktop/mobile一致。
- 账户创建按newVenue判断唯一性；手动下单显式传行venue并由服务端核对。
- API错误只由一层写response；无效ID返回一个合法JSON对象。
- 手动execute确认说明既可能买入也可能止损，不把scan、对账与新交易混成同一按钮含义。

这些小切片可以独立交付，但不能代替服务器的幂等、作用域校验和风险准入。
